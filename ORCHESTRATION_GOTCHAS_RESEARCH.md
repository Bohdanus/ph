# Parallel-Agent Coordination: Evidence Audit

**Status:** Replaces the earlier draft of this report. Reviewed against the repository state at `d0e5750ce` on 2026-11-10.

## Bottom Line

The earlier report is not a safe basis for changing project policy. It mixed real research with unsupported generalizations, stale repository descriptions, and runnable examples that conflict with this repository's worktree and landing procedures. Those examples and speculative recommendations have been removed.

The current system already has substantial safeguards: per-task worktrees, scoped task briefs, a shared swarm board, a guarded and owner-tracked main landing path, merge-takeover checks, repository-state reporting, and isolated E2E servers. The remaining coordination weaknesses are bounded: planned file-set overlap is reviewed by people rather than checked by a script; same-branch writers are indistinguishable to board locks; and the merge guard is not a general semantic-correctness analyzer.

**Recommendation:** keep the existing workflow. Require explicit, disjoint write paths for concurrent writers and use the existing board claims where they apply. Do not add a merge queue, CRDT editing, generic runtime-provisioning scripts, or a semantic-conflict gate on the strength of this report. Consider an advisory planned-path overlap check only if project evidence shows repeated avoidable collisions.

## Audit Method

Ten first-pass and seven final-draft, read-only free-model audits were used to locate repository claims, challenge recommendations, and identify sources. Their answers disagreed and included claims contradicted by the repository or primary sources. They were treated as leads, not evidence. The material findings below were rechecked against project files or the cited primary sources. No agent output is cited as authority.

## Current Project Facts

### Isolation and task boundaries

- `AGENTS.md` requires tracked work in a task worktree under `.kilo/worktrees/`, on its own branch. The main worktree is for reading and pinned landings, not ordinary edits.
- A brief must name Goal, Owner, Worktree, Paths, Dependencies, Proof, and Handoff. Concurrent writers need disjoint path scopes. A Kilo `task` child inherits the caller's worktree; it does not create a new worktree. Free research children are read-only, and the coordinator owns Git operations.
- This is a consequential boundary, not a theoretical warning: `docs/ORCHESTRATION.md` records 1,398 `task` subagents using the primary checkout as their directory in one measured seven-day window, plus 22 Agent Manager local sessions editing it. That evidence supports creating/confirming the worktree before fan-out; it does not show that an overlap checker would prevent wrong-checkout writes.
- Worktrees separate working files, `HEAD`, and index, while sharing the repository's common Git data and most refs. The repository's prohibition on `git stash` is a project rule grounded in the common unordered stash stack and recorded incidents, not a general claim that worktrees share an index.
- Writers sharing one checkout also share its index, which has no per-writer attribution. The project records four sessions that found another writer's paths staged; checking for `.git/index.lock` did not reveal those completed staging operations. Follow the [Landing procedure](docs/ORCHESTRATION.md#landing): inspect `git diff --cached --stat` before every `git add`, stage named paths, and leave unknown staged paths untouched.
- `git worktree lock` protects a worktree from pruning/moving/removal in the cases described by Git; it is not this project's agent/file lock. Agent coordination uses the swarm board.

### Swarm board and its limits

- `npm run swarm` uses a SQLite board shared by the repository worktrees. It tracks issues, file references, file locks, and agent presence. `hold`, `claim --files`, and `check` are explicit workflow operations, not automatic pre-dispatch enforcement.
- Board identity is based on the Git branch. Two writers in one worktree therefore look like the same board agent; both can hold the same path without a foreign-lock refusal. The project explicitly treats one writer per worktree and disjoint subagent paths as discipline, not as something the board can guarantee.
- A board file claim is not a lock on `refs/heads/main`. Nor does an empty board answer prove no one is working.

### Merge and landing controls

- Reviewed landings use `npm run main:landing -- land ...` with pinned main SHA, incoming candidate SHA, tree, source branch, and chat ID. The wrapper takes an owner lease and invokes the reviewed-landing helper. Use `npm run main:landing -- status` to inspect occupancy; an active owner or dirty/unowned operation is a stop, not an invitation to create a competing landing.
- Main must first be merged or rebased into the candidate branch in that branch's own worktree; review and rerun gates on the resulting candidate. The main landing is then a mechanical prepared `--no-commit --no-ff` merge. Do not resolve conflicts in main. The project has an explicit procedure for pinned landing, takeover, and exact orphan `AUTO_MERGE` recovery.
- `merge-takeover-guard.mjs` is a narrow, adversarially tested content-loss detector for specific silent whole-file takeover shapes. It is not a language-aware semantic analyzer and does not prove behavioral correctness. Ordinary prepared merges are guarded at their commit boundary, but fast-forward creates no blocking hook event, `git merge --squash -X ours` can avoid a commit/`MERGE_HEAD`, and `--no-verify` bypasses hooks. Hand-edited clean resolutions are not a complete detector target; see [Landing](docs/ORCHESTRATION.md#landing) and [What git is doing right now](docs/ORCHESTRATION.md#what-git-is-doing-right-now).
- `npm run repo:state` reports in-progress Git operations and unreadable state across worktrees. It is deliberately not a hook or global lock; exit 1 can mean an operation is in progress or the state could not be read. Disposal separately refuses these unsafe/unreadable conditions. The worktree inventory and `npm run branches:orphan` provide separate ownership/classification views.

### Test and runtime isolation

- `npm run test:e2e` starts its own server with a run-specific port and output directory. The swarm E2E slot reduces simultaneous runs but is advisory and is not the correctness boundary. It uses an `e2e-run/<branch>/<pid>` identity because ordinary board identity is branch-based; inability to take the slot does not stop the run.
- That guarantee is specific to the E2E wrapper. It is not a general per-worktree dev-server, database, cache, or environment provisioner. The repository documents no recurring shared-database or environment collision that would justify a generic provisioner.
- Worktree dependency behavior is repository-specific: Node may resolve dependencies from an ancestor checkout, while Vite does not resolve assets that way. The project docs call out when a local install is needed; "run `npm ci` in every worktree" is not its policy.
- Stage only owned paths. The project specifically bans `git add -A` in a shared/dirty checkout and `git stash`; merge-takeover checks and reviewed landing pins do not make those unsafe operations safe.

## Conflict Classes and Coverage

| Class                     | Meaning                                                                                                    | Project treatment                                                                                                                                                                                             |
| ------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Textual merge conflict    | Git cannot combine overlapping edits and leaves unresolved paths                                           | Inspect and resolve in the candidate worktree; `repo:state` reports outstanding operations. Never resolve in main.                                                                                            |
| Silent content takeover   | A merge or stale worktree silently selects/discards a whole-file version without ordinary conflict markers | The narrow `merge-takeover-guard` catches documented shapes at its supported commit boundary; its own docs specify uncovered cases.                                                                           |
| Semantic/program conflict | The composition builds or merges but behavior, assumptions, or interfaces are wrong                        | Not generally detectable by Git or the takeover guard. Use the project review and test gates, and verify the composed candidate. No single external analyzer cited here establishes a complete semantic gate. |

These classes must not be conflated. "No Git conflict" means the merge algorithm produced a tree; it does not prove that the code behaves correctly. Conversely, a proposed semantic analyzer is not a complete correctness proof merely because it finds selected cross-file rename cases.

## Conclusion

The project already addresses the high-cost failure modes it has actually observed: accidental shared-main work, cross-session path coordination, silent merge takeovers, incomplete landing ownership, in-progress Git operations, and E2E attachment to another checkout. The report does not establish that a new script or external tool would improve those controls enough to justify added failure modes.

The prudent next step is operational, not architectural: keep each writer's declared paths disjoint, use board locks where they distinguish agents, synchronize and review the exact candidate, run the appropriate gates, and land through the owner-tracked pinned flow. Collect evidence about any repeated residual collision before adding automation.
